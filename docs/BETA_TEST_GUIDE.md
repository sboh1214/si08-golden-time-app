## 1. 테스트 빌드 만들기

설치 파일은 Expo 의 클라우드 빌드 서비스(EAS Build)로 만듭니다. 로컬에 Xcode·Android Studio 가 없어도 됩니다.

### 1.1 빌드 프로필

`eas.json` 에 정의되어 있습니다.

| 프로필 | 설치 방식 | API | 언제 쓰나요 |
| --- | --- | --- | --- |
| `preview` | 내부 배포 (Android **APK**, iOS ad hoc) | 내장 데모 서버 | **베타테스트·시연 기본값** — 백엔드 없이 모든 기능 확인 |
| `preview-api` | 내부 배포 | 실서버 | 백엔드 연동 베타테스트 (`EXPO_PUBLIC_API_BASE_URL` 을 실제 주소로 바꾼 뒤 — 자리표시자 `https://api.example.com` 그대로 빌드하면 앱이 '서비스 연결 설정이 필요해요' 화면에서 멈춥니다) |
| `development` | 내부 배포 | 내장 데모 서버 | 설정 › 정보에 '개발' 환경으로 표시되는 일반 내부 빌드 (개발 서버에 연결하는 개발용 클라이언트(dev client)는 아님) |
| `production` | 스토어 제출용 | 실서버 | 정식 출시 (본 가이드 범위 밖) |

### 1.2 준비 (최초 1회)

```bash
git clone <저장소 주소> && cd <저장소 폴더>
npm install
npm install -g eas-cli        # 또는 이후 명령마다 npx eas-cli@latest 사용
eas login                     # Expo 계정 로그인 (계정이 없으면 expo.dev 에서 가입)
```

- 첫 빌드 때 EAS 프로젝트를 만들지 묻습니다. 승인하면 `app.json` 에 프로젝트 ID(`extra.eas.projectId`)가 추가되니 저장소에 커밋해 두세요.
- 정식 운영을 고려해 Expo 계정은 **발주처 명의(조직 계정)** 로 만드는 것을 권장합니다. 서명 키가 그 계정에 보관됩니다.

### 1.3 Android 테스트 빌드 (APK)

```bash
npm run build:preview:android
# = eas build --profile preview --platform android
```

1. 처음 빌드하면 Android 서명 키(keystore) 생성 여부를 묻습니다 → **Yes** (EAS 가 안전하게 보관).
2. 빌드가 끝나면(보통 10~20분) 터미널과 expo.dev 빌드 페이지에 **설치 링크와 QR 코드**가 표시됩니다.
3. 이 링크를 테스터에게 공유합니다. 링크를 아는 사람은 누구나 내려받을 수 있으니 공유 범위에 주의하세요 (expo.dev 프로젝트 설정에서 로그인한 사용자만 받도록 바꿀 수 있습니다).

### 1.4 iOS 테스트 빌드 (ad hoc)

iOS 는 Apple 정책상 **미리 등록한 기기에만** 테스트 빌드를 설치할 수 있습니다.

1. **Apple Developer Program**(유료) 계정을 준비합니다 (발주처 명의 권장).
2. 테스터 기기를 등록합니다.
   ```bash
   eas device:create
   ```
   생성된 등록 링크(QR)를 테스터가 **iPhone 의 Safari** 로 열어 프로필을 설치하면 기기 정보(UDID)가 등록됩니다.
3. 빌드합니다.
   ```bash
   npm run build:preview:ios
   # = eas build --profile preview --platform ios
   ```
   Apple 계정 로그인을 요청하면 로그인합니다. EAS 가 등록된 기기를 포함한 프로비저닝 프로필을 만듭니다.
4. 빌드 페이지의 설치 링크를 등록된 iPhone 에서 엽니다.

- 기기를 새로 등록하면 **다시 빌드**해야 그 기기에 설치할 수 있습니다.
- 새로 가입했거나 갱신한 Apple 계정은 기기 등록 처리에 최대 24~72시간이 걸릴 수 있습니다.
- 등록된 기기 확인: `eas device:list`

### 1.5 실서버 연동 빌드 (선택)

백엔드가 준비되면 `eas.json` 의 `preview-api` 프로필에서 `EXPO_PUBLIC_API_BASE_URL` 을 실제 주소로 바꾼 뒤 빌드합니다.

```bash
eas build --profile preview-api --platform android
```

설치 후 설정 › 서비스 연결에서 'API 모드: 실서버'와 연결 상태 '정상'을 확인합니다. 연동 규칙은 [API 계약서](./API_CONTRACT.md)를 참고하세요.

> API 모드와 서버·AI 모델 버전은 개발·베타 빌드(또는 내장 데모 서버로 동작할 때)에만 보입니다. 정식(`production`) 빌드의 설정 화면은 연결 상태(정상·연결 안 됨·점검 중)만 보여 줍니다.

> 배포용 빌드(`EXPO_PUBLIC_APP_ENV` 가 `beta`·`production`)는 서버 설정이 잘못되면 조용히 데모 서버로 동작하지 않고, 앱 시작 시 '서비스 연결 설정이 필요해요' 화면을 띄운 뒤 멈춥니다.
> - `http` 모드인데 `EXPO_PUBLIC_API_BASE_URL` 이 비어 있음
> - 주소가 자리표시자(`example.com` 등)
> - `production` 빌드가 데모 서버(`mock`)로 설정됨

### 1.6 빌드 기록

테스트 빌드를 만들 때마다 아래 표에 한 줄씩 남겨 테스터·검수 담당자가 어떤 빌드를 설치했는지 확인할 수 있게 합니다. 빌드 ID 와 설치 링크는 빌드가 끝난 뒤 터미널 또는 expo.dev 빌드 페이지에 표시됩니다 (`eas build:list` 로 다시 볼 수 있음).

| 빌드 일자 | 프로필 | 플랫폼 | 앱 버전 (빌드 번호) | EAS 빌드 ID | 설치 링크 · QR | 비고 |
| --- | --- | --- | --- | --- | --- | --- |
| (첫 빌드 후 기입) | `preview` | Android | 1.0.0 (1) | | | |

### 1.7 테스트 기간 중 오류 수정 배포

이 앱은 무선 업데이트(OTA, `expo-updates`)를 사용하지 않습니다. 베타테스트 중 발견된 오류를 고치면 다음 순서로 전달합니다.

1. 수정 후 `npm run verify` 통과 확인, `CHANGELOG.md` 에 수정 내용 기록.
2. 같은 프로필로 **다시 빌드**합니다 (`npm run build:preview:android` / `:ios`). 빌드 번호는 EAS 가 관리하며(`appVersionSource: remote`), `preview` 프로필은 빌드할 때마다 1씩 올라갑니다(`autoIncrement`). 설치한 빌드는 설정 › 정보 › 앱 버전에 `1.0.0 (7)` 처럼 표시되어 테스터가 어느 빌드를 쓰는지 구분할 수 있습니다.
3. 1.6 빌드 기록에 새 줄을 추가하고 새 설치 링크를 테스터에게 공유합니다.
4. 테스터는 새 버전을 **덮어 설치**합니다 (Android 는 데이터 유지). iOS 는 이미 등록된 기기에만 설치되며, 새 기기는 등록 후 다시 빌드해야 합니다.

> 무선 업데이트가 필요해지면 `npx expo install expo-updates` → `eas update:configure` 로 설정하고, 빌드 프로필마다 다른 채널(`preview`·`preview-api`·`production`)을 지정해 데모 서버용 수정이 실서버 빌드로 가지 않게 합니다.

## 2. 설치 방법

### Android

1. 전달받은 설치 링크(또는 QR 코드)를 휴대폰에서 엽니다 → **APK 다운로드**.
2. 다운로드한 파일을 엽니다. "출처를 알 수 없는 앱" 설치를 허용할지 물으면 브라우저(또는 파일 앱)에 대해 **허용**합니다.
3. Google Play 프로텍트 경고가 나오면 '세부정보 더보기 › 무시하고 설치'를 선택합니다 (스토어 심사를 거치지 않은 테스트 앱이라 표시되는 경고입니다).
4. 앱 이름 **건강수첩** 으로 설치됩니다. 새 버전은 같은 방법으로 덮어 설치하면 데이터가 유지됩니다.

### iOS

1. 기기 등록(1.4의 2단계)을 마친 iPhone 에서 설치 링크를 엽니다 → **설치**.
2. iOS 16 이상에서는 처음 실행 전에 **설정 › 개인정보 보호 및 보안 › 개발자 모드** 를 켜고 재시동해야 할 수 있습니다.

### 웹 (시연용)

개발 PC 에서 `npm install` 후 `npm run web` 을 실행하면 브라우저에서 앱이 열립니다. 발표·화면 공유 시연에 편리합니다.

### Expo Go (개발자용)

`npm start` 후 표시되는 QR 코드를 Expo Go 앱으로 스캔합니다. 기기의 Expo Go 가 SDK 58 을 지원해야 합니다.

## 3. 시연 시나리오

내장 데모 서버(`preview` 빌드, 웹, Expo Go)를 기준으로 과업 ①~⑤를 순서대로 보여 주는 약 10~15분 분량의 시나리오입니다.

### 시연 준비

1. 설정 › 개발자 도구 › **데모 데이터 초기화** → 샘플 진료기록이 들어 있는 처음 상태로 되돌립니다.
2. 설정 › 개발자 도구 › **AI 처리 시간: 빠르게 4초** 로 바꾸면 등록 시연이 짧아집니다.
3. 오류 발생률 0%, 응답 지연 0.5초(기본값), '다음 업로드 분석 실패시키기' 꺼짐 상태인지 확인합니다.
4. 실기기에서 촬영 시연을 하려면 진료기록 예시 종이(개인정보가 없는 샘플)를 준비합니다.

> 데모 서버는 **올린 사진의 실제 내용과 관계없이 샘플 해설을 만듭니다.** 실제 글자 인식·해설은 백엔드 AI 해설 API 연동 후 동작합니다.

### 0) 온보딩 — 첫 실행

1. 안내 3쪽을 넘깁니다 (다음 / 건너뛰기).
2. 동의 화면에서 **AI 해설은 참고용**임을 이해했다는 항목과 **진료기록(민감정보) 처리 동의** 항목(모두 필수)을 체크합니다 (또는 '모두 동의해요').
3. **동의하고 시작하기** → 홈 화면.

> 이미 온보딩을 마쳤다면 설정 › 정보 › **처음 안내 다시 보기** 로 다시 볼 수 있습니다.

### 1) 홈 둘러보기

- **진료기록 등록하기** 카드, 처리 중·분석 실패 기록 알림, 최근 진료기록, **확인이 필요한 검사**, **다음 진료 때 물어볼 질문** 요약을 보여 줍니다.

### 2) ① 문서 등록

1. 홈 › **진료기록 등록하기**.
2. **카메라로 촬영**(실기기) 또는 **사진에서 선택**(여러 장 가능) / **PDF 파일 선택**.
3. 미리보기에서 페이지를 **앞뒤로 옮기기**, 페이지 추가·빼기를 보여 줍니다.
4. 기록 정보 입력: 기록 종류, **병원 이름**, **진료일**, (선택) 진료과·제목.
   - 병원 이름을 비운 채 진행하면 입력 오류 안내가 나오는 것도 보여 줄 수 있습니다.
5. **AI 해설 받기** → 업로드 진행률 → '업로드 → 글자 인식 → 항목 정리 → 쉬운 해설' 단계가 차례로 진행됩니다.
6. **해설이 완성됐어요** 요약(진단·검사·처방 약 개수) → **정리 결과 보기**.

### 3) ② 정리 결과

- 기록 요약, **진단명**(확진·의심 구분), **검사 항목**(판정 요약), **처방 약**(먹는 방법·처방 기간·주의사항)을 차례로 보여 줍니다.
- 진단·검사·처방 약 항목의 **원문 보기** 를 눌러 근거 문장으로 이동할 수 있음을 보여 줍니다.

### 4) ③ 원문 대조 해설

1. 화면 상단 탭 **원문 대조 해설**.
2. 원문 문장과 쉬운 해설이 짝지어 나오는 것을 보여 주고, 헤더 버튼으로 **나란히 / 위아래** 배치를 바꿔 봅니다. (아주 좁은 화면이나 글자 크게 보기를 켠 작은 화면에서는 자동으로 위아래로 보이고, '이렇게 읽어요' 안내에 이유가 나옵니다.)
3. 강조된 의학 용어를 눌러 **용어 풀이**를 엽니다.
4. '의료진 확인 권장' 표시가 있는 문장(신뢰도가 낮은 해설)을 보여 줍니다.
5. **글자 크게** 를 켜서 큰 글씨 보기를 보여 줍니다.

### 5) ④ 검사 수치 시각화

1. 화면 상단 탭 **검사 수치** — 참고치 막대 위의 측정값 위치와 판정(색·아이콘·글자)을 설명합니다. '확인 필요' 필터를 눌러 봅니다.
2. 검사 항목을 눌러 **수치 변화** 화면으로 이동 → 수치 변화 그래프, 지난 검사 대비 변화, 측정 기록.
3. (선택) 홈 › 확인이 필요한 검사 › **전체 보기** 로 **내 검사 수치** 목록을 보여 줍니다.

### 6) ⑤ 질문 리스트

1. 진료기록의 정리 결과 화면 › **AI 추천 질문 받기** → 마음에 드는 질문 **담기**.
2. 하단 **질문 노트** 탭 → 담은 질문 확인 → **질문 쓰기** 로 직접 질문 추가(관련 진료기록 선택 가능).
3. 질문의 체크박스를 눌러 **물어봤어요** 처리 → '물어본 질문' 필터에서 확인, 질문을 열어 **의사 답변 메모** 저장.
4. **진료실 모드** → 물어볼 질문이 큰 글씨 전체 화면으로 표시됩니다 (진료실에서 의사에게 보여 주는 용도).

### 7) ⑤ 건강 타임라인

1. 하단 **타임라인** 탭 → 요약(기록 수·병원 수·기간)과 월별로 묶인 진료·진단·검사·처방.
2. 분류 필터(진료·진단·검사·처방)를 바꿔 봅니다.
3. 검사 항목의 **수치 변화 보기** 로 항목별 변화를, 진료 항목의 **정리 결과 보기** 로 해당 기록을 엽니다.

### 8) 실패 → 다시 분석 경로 (과업 ①⑥)

1. 설정 › 개발자 도구 › **다음 업로드 분석 실패시키기** 켜기. 이 설정은 **다음에 등록하는 기록 1건에만** 적용되고, 적용되면 저절로 꺼집니다 (다시 끌 필요 없음).
2. 2)의 방법으로 진료기록을 하나 더 등록 → 처리 도중 실패 안내(분석 실패 표시와 실패 사유)가 나옵니다.
3. **다시 분석하기** → 처리 단계가 다시 진행되어 완료됩니다. (실패한 기록을 나중에 열어도 같은 버튼이 있습니다.)

### 9) 오류·로딩 상태 (과업 ⑥)

> 탭 화면은 한 번 열면 내용을 기억하므로 탭을 오가기만 해서는 서버에 요청하지 않습니다. 아래처럼 실제로 요청이 나가는 동작으로 보여 줍니다.

1. 설정 › 개발자 도구 › **응답 지연 3초** → **데모 데이터 초기화** → 곧바로 홈·내 기록 탭을 열어 로딩 표시를 보여 줍니다. 아직 열지 않은 진료기록을 열어도 로딩 표시가 나옵니다.
2. **오류 발생률 50%** → 아직 열지 않은 진료기록을 몇 번 열어 봅니다 → 자동 재시도(최대 2회)까지 모두 실패하면 오류 안내와 **다시 시도**.
3. 같은 설정에서 내 기록을 **당겨서 새로고침**하거나 질문을 저장해 봅니다 → 새로고침이 실패하면 목록은 그대로 두고 상단에 '최신 내용을 불러오지 못했어요 · 다시 불러오기', 저장이 실패하면 실패 안내 대화상자.
4. 끝나면 응답 지연 '0.5초'(기본값), 오류 발생률 '0%' 로 되돌립니다.

### 시연 마무리

설정 › 개발자 도구 › **데모 데이터 초기화** 로 다음 시연을 위해 처음 상태로 되돌립니다.

## 4. 오류 상태 재현 방법

설정 › **개발자 도구** 는 내장 데모 서버로 동작할 때만 보입니다 (실서버 빌드에서는 숨김). 바꾼 값은 앱을 다시 실행해도 유지됩니다.

| 개발자 도구 항목 | 선택지 | 하는 일 |
| --- | --- | --- |
| 응답 지연 | 없음 · 0.5초(기본값) · 1.5초 · 3초 | 모든 요청이 평균 이만큼 늦게 응답 |
| 오류 발생률 | 0% · 20% · 50% | 요청이 이 확률로 네트워크·서버 오류로 실패 |
| 다음 업로드 분석 실패시키기 | 켜기 | 다음에 등록하는 기록 **1건**의 AI 분석이 처리 도중 실패, 적용되면 저절로 꺼짐 |
| AI 처리 시간 | 빠르게 4초 · 보통 9초 · 느리게 20초 | 업로드 후 해설 완성까지 걸리는 시간 |
| 데모 데이터 초기화 | — | 샘플 데이터 상태로 되돌림 (등록한 기록·질문 삭제) |

| 확인할 상태 | 재현 방법 | 기대 결과 |
| --- | --- | --- |
| 로딩 | 응답 지연 3초 → 데모 데이터 초기화 직후 탭 열기, 또는 아직 열지 않은 기록 열기 | 로딩 표시 후 내용 표시 |
| 네트워크·서버 오류 (처음 조회) | 오류 발생률 50% → 아직 열지 않은 기록 열기 반복 | 자동 재시도(최대 2회) 후에도 실패하면 오류 안내와 **다시 시도** 버튼 |
| 네트워크·서버 오류 (새로고침) | 오류 발생률 50% → 내용이 있는 화면에서 당겨서 새로고침 반복 | 내용은 그대로 두고 상단에 '최신 내용을 불러오지 못했어요 · 다시 불러오기' (작성 중인 메모·진료실 모드 유지) |
| 네트워크·서버 오류 (저장) | 오류 발생률 50% → 질문 저장·물어봤어요 체크 반복 | 실패 안내 대화상자, 체크는 원래 상태로 되돌아감 (저장 요청은 자동 재시도하지 않음) |
| 처리 중 | AI 처리 시간 '느리게 20초' → 진료기록 등록 → **닫고 기다리기** | 홈 알림·내 기록에 진행률 표시, 완료되면 목록·확인이 필요한 검사·타임라인 자동 갱신 |
| 분석 실패 | 다음 업로드 분석 실패시키기 → 진료기록 등록 | 등록 방법에 맞춘 실패 사유 안내(PDF 는 다른 파일 안내), **다시 분석하기** 로 복구 |
| 빈 상태 | 질문 노트의 질문을 모두 삭제 / 내 기록에서 검색어로 결과 없음 | 상황에 맞는 빈 상태 안내와 다음 행동 버튼 |
| 오프라인 (실서버 빌드) | 비행기 모드 켜기 → 아직 열지 않은 기록 열기 / 당겨서 새로고침 | 인터넷 연결 확인 안내와 다시 시도 (내용이 있던 화면은 상단 안내) |
| 동의 전 접근 | 온보딩을 마치지 않은 상태에서 `healthnote://upload` 링크 또는 웹 주소 `/upload` 열기 | 동의 화면으로 이동 |
| 서버 점검 (실서버 빌드) | 백엔드가 `GET /health` 에 `ok: false` 응답 | 설정 › 연결 상태 '점검 중' |

## 6. 알려진 제약

- **샘플 해설** — 데모 서버는 올린 진료기록 내용과 관계없이 샘플 해설 템플릿으로 결과를 만듭니다. 실제 글자 인식·해설은 백엔드 AI 해설 API 연동 후 확인할 수 있습니다.
- **기기 내 저장** — 데모 서버의 데이터는 그 기기(웹은 그 브라우저)에만 저장됩니다. 앱을 삭제하면 사라지고 다른 기기와 동기화되지 않습니다.
- **처리 진행** — 데모 서버의 AI 처리는 등록 시각 기준으로 진행되므로, 처리 중에 앱을 껐다 켜도 이어서(또는 이미 완료된 상태로) 보입니다.
- **iOS 설치** — 등록된 기기에만 설치할 수 있고, 기기를 추가하면 다시 빌드해야 합니다.
- **웹** — 시연용입니다. '카메라로 촬영'은 브라우저의 파일 선택으로 대신하며(휴대폰 브라우저에서는 사진 찍기 선택 가능), 진동(햅틱) 피드백은 없습니다.
- **인증 없음** — 회원·로그인 기능은 과업 범위에 포함되지 않았습니다. 실제 환자 정보로 테스트하지 마세요.
- **Expo Go** — 설치된 Expo Go 가 SDK 58 을 지원하지 않으면 실행되지 않습니다. 이 경우 테스트 빌드를 사용하세요.
